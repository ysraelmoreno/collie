Interceptador HTTP — viabilidade

Análise de viabilidade · 2026-10-30 · painel "Rede" para emulador Android no Collie, no estilo HTTP Toolkit. Só pesquisa + plano, nada implementado.

Sumário

    Recomendação

    Viável. Proxy MITM nativo em Swift (SwiftNIO + NIOSSL + swift-certificates), rodando no daemon collied, e um novo plugin network preso ao serial do emulador. No MVP o emulador é configurado por adb reverse + settings put global http_proxy, e a CA vai para o system store por adb root + tmpfs/nsenter, no estilo HTTP Toolkit. A conta fica em ~3 semanas, mais um spike de 2–3 dias.

    Por quê:

    • O daemon já cuida de tudo do Android: o caminho do adb, a vida do emulador, os eventos e o streaming para os painéis. O proxy é mais um serviço de vida longa nesse mesmo lugar, e a captura continua mesmo com o painel fechado.
    • O NIOSSL aceita cert e chave em memória (DER/PEM) e troca o contexto por SNI. Com o Network.framework seria preciso uma SecIdentity, e no macOS isso obriga a passar pelo Keychain para cada host. Esse é o maior atrito da alternativa nativa da Apple.
    • Embutir mitmproxy ou Go traria um runtime estranho, notarização de binário de terceiros, dezenas de MB e uma ponte IPC. O ganho (HTTP/2 e WebSocket prontos) só pesa depois do MVP.
    • Combina com o jeito "agente primeiro" do Collie: collie network list/get/curl sai quase de graça pelo mesmo CommandRouter.

    2. Como o HTTP Toolkit faz

    Captura

    • Caminho principal: app VPN no Android. Ela pega os pacotes TCP das portas comuns (80, 443, 8000, 8080…) e manda para o desktop. No Android 10+ ela também define um proxy HTTP padrão. Cobre apps que ignoram proxy, mas exige um APK nosso e o aviso de VPN.
    • Proxy simples, a escolha do nosso MVP: 
      adb -s $S reverse tcp:8899 tcp:8899
adb -s $S shell settings put global http_proxy 127.0.0.1:8899
# desfazer (delete só vale após reboot; ":0" vale na hora)
adb -s $S shell settings put global http_proxy :0
adb -s $S reverse --remove tcp:8899
      O reverse deixa o proxy preso ao loopback do Mac. Alternativa no emulador: 10.0.2.2 = loopback do host, sem reverse. Limite: Flutter/Dart, apps com Proxy.NO_PROXY e UDP/QUIC ignoram o proxy.

    CA no system store (precisa de root)

    • Android ≤13: adb root, depois tmpfs montado sobre /system/etc/security/cacerts, copiando de volta as CAs existentes e juntando <subject_hash_old>.0. chmod 644, chcon u:object_r:system_file:s0. Vale na hora e some no reboot.
    • Android 14+: as CAs vêm do APEX /apex/com.android.conscrypt/cacerts, imutável. Os passos:
      1. Montar um tmpfs com as CAs atuais + a nossa.
      2. nsenter --mount=/proc/<zygote|zygote64>/ns/mnt -- mount --bind tmp /apex/com.android.conscrypt/cacerts
      3. Fazer o mesmo em cada filho do zygote (apps já abertos), em paralelo. Leva menos de 1 s.
      Temporário: some no reboot e reaplicamos no attach.
    • Imagens: google_apis e AOSP aceitam adb root. google_apis_playstore não aceita: só dá para usar CA de usuário, em que apps target ≥24 não confiam.

    Limitações que herdamos

    • network_security_config só importa para CA de usuário. Com a CA no sistema, ~99% dos apps confiam. Para app próprio sem root: <debug-overrides><trust-anchors><certificates src="user"/>.
    • Certificate pinning (bancos, OkHttp CertificatePinner) quebra a conexão. O HTTP Toolkit resolve com Frida (unpinning) ou apk-mitm. Fora do MVP: a gente detecta (handshake abortado) e mostra "pinned?".
    • HTTP/2: se o MITM anunciar só http/1.1 no ALPN, OkHttp e Cronet caem para h1. gRPC precisa de h2 e falha. Fica para depois do MVP.
    • WebSocket: o MVP registra o handshake (101) e repassa os frames como túnel cego. Os frames vêm depois.

    CA e certificados

    • CA própria por instalação: P-256 ou RSA-2048, gerada no primeiro attach com swift-certificates (Certificate, BasicConstraints.isCertificateAuthority, KeyUsage.keyCertSign). Validade de 1 ano, rotação manual.
    • Leaf por host sob demanda: SAN = SNI (ou IP), validade de 7 dias, cache LRU em memória (~500). Assinar com P-256 leva ms.
    • Nome do arquivo no Android: subject_hash_old (MD5 do subject DER, estilo OpenSSL ≤0.9.8). Tem que calcular em Swift. Item de spike.

    4. Modelo de dados + cURL

    struct Flow: Codable, Sendable, Identifiable {
  let id: UInt64; let serial: String; let started: Date
  var method: String; var url: String          // absoluta: scheme://host:port/path?query
  var httpVersion: String                       // "HTTP/1.1" | "HTTP/2"
  var reqHeaders: [Header]; var reqBody: Body?
  var status: Int?; var resHeaders: [Header]; var resBody: Body?
  var timing: Timing                            // dns/connect/tls/ttfb/total
  var state: State                              // pending | done | failed(String) | tunneled
  var tls: TLSInfo?                             // sni, alpn, pinnedSuspect
}
struct Header: Codable, Sendable { let name: String; let value: String }  // ordem e duplicatas preservadas
struct Body: Codable, Sendable {
  let size: Int; let truncated: Bool
  let encoding: String?                          // content-encoding original
  let stored: Ref                                // .inline(Data) ≤64 KiB | .file(URL) no runDir
}

    A lista mostra só um resumo (id, método, host, path, status, tamanho, ms). O detalhe pede network.get id. No evento network.flow vai só o resumo, nunca o body.

    Copiar como cURL (CollieNetwork, puro, com teste)

    • Aspas simples POSIX: ' vira '\''. Vale para URL, cada -H 'Name: value' e o body texto.
    • -X METHOD só quando não é implícito (GET sem body, POST com body).
    • Ficam de fora os headers hop-by-hop e os que o curl recalcula: Content-Length, Connection, Transfer-Encoding, Proxy-*, pseudo-headers h2 (:authority vira Host só se for diferente da URL). Accept-Encoding com gzip/br/deflate vira --compressed.
    • Body UTF-8 válido sem NUL: --data-raw '…'. Binário (ou não-UTF-8): 
      printf %s 'BASE64…' | base64 -d | curl … --data-binary @-
      Acima de ~256 KiB o body vai para um arquivo temporário (--data-binary @/path) com aviso.
    • Multipart: mandar o corpo bruto com o Content-Type e o boundary originais (--data-binary). É fiel byte a byte; reconstruir com -F perderia ordem e nomes.
    • --http2 quando o fluxo foi h2. Sem -k: o cURL aponta para o servidor real.

    Decode para exibir (a cópia em cURL e o forward usam os bytes originais)

    • gzip/deflate: libz do sistema (inflateInit2 com window 31/-15).
    • br: Compression.framework COMPRESSION_BROTLI (macOS 12+). Confirmar no spike se descomprime streams HTTP arbitrários.
    • zstd: sem suporte nativo, exibe "não decodificado". Fica para depois.

    5. Riscos

    RiscoMitigação
    Chave privada da CA vazar: quem tiver a chave faz MITM de qualquer device que confie nela.A chave fica num item do Keychain (generic password, só o daemon lê) ou num arquivo 0600 em Application Support, nunca no repo nem no projeto. A CA nunca entra no trust store do macOS. Ela só é injetada em memória (tmpfs) nos emuladores escolhidos. Ter "Regenerar CA" e "Esquecer CA".
    Proxy exposto na redeBind só em 127.0.0.1; o device chega via adb reverse. Recusar destino 127.0.0.1:porta-do-proxy (loop). Porta efêmera por attach.
    Escopo além do emuladorMVP: só emulator-* com adb root funcionando. O detach, o fechamento do painel e o stop do daemon desfazem o proxy e o reverse. O crash do daemon deixa o proxy setado (o device fica sem rede), por isso reconciliar no próximo start, como o OrphanReaper.
    Dados sensíveis capturados (tokens, cookies)Store em memória, com spill em runDir 0600, apagado no clear e no stop. CLI/MCP segue a regra de leash do device (só quem alcança o painel lê). Comando clear.
    SandboxApp fora do App Sandbox (sem entitlements), daemon via launchd. Bind em loopback não dispara o firewall. Se um dia entrar no sandbox: com.apple.security.network.server/client.
    Performance / bodies grandesStreaming (o forward nunca espera o body inteiro). A captura tem teto de 10 MiB por body (flag truncated) e o store tem ring buffer (~2k fluxos / 512 MiB em disco). Downloads e vídeo passam sem guardar.
    Pinning e apps que ignoram proxyMostrar como falha "TLS recusado: pinning?" ou nem aparecer. Documentar. Pós-MVP: iptables (root) para modo transparente e Frida.
    Android 15/16 mudar o APEX ou o zygoteSpike em API 34, 35 e 36. Fallback com a Option 2 (remount de /apex) + restart do system_server.
    Dependências NIO no buildIsolar no target CollieNetwork/DaemonKit. App e CLI não linkam NIO.

    Outros achados

    • subject_hash_old em Swift: 130/130 iguais ao openssl@3 x509 -subject_hash_old (128 roots do macOS, a CA de teste com subject UTF-8 e a CA do mitm c8750f0d). Isso exigiu ler só os bytes do subject no TBSCertificate via SwiftASN1: o parse completo do swift-certificates rejeita roots reais com serial negativo (ASN1Error.invalidASN1IntegerEncoding: INTEGER encoded with top bit set). Com mitmdump o hash pode até sair do openssl, mas a versão Swift está pronta e não depende de binário externo.
    • Proxy prévio do device: proxy-on.sh salva o valor de http_proxy e proxy-off.sh o restaura. Isso importa porque o 5554 já usava o Proxyman.
    • Emulador com GPU por software e 2 cores: load ~30 e ANRs de System UI e Launcher. São da carga, não da injeção. Para testes, preferir hw.gpu.mode=host.
    • O SDK não tem avdmanager: o AVD descartável foi criado escrevendo config.ini à mão (já apagado). Para repetir, instalar cmdline-tools.

    Go / no-go

    GO para o MVP com mitmdump como backend, com três ajustes no plano:

    1. O network.attach injeta a CA no store de sistema (tmpfs + nsenter) e no de usuário (cacerts-added, por causa do Chrome), e o detach remove dos dois.
    2. O poll de devices do DeviceService reaplica adb reverse. Ao subir o daemon e ao ver reboot, limpa o http_proxy que aponte para uma porta nossa sem attach vivo.
    3. Fase 1 vira "subprocesso mitmdump + parser JSONL" (estimativa cai de 4–6 d para ~2–3 d). As fases 2–4 ficam como estão.

    Pendentes, a decidir pelo dono: baixar imagens API 34/35/36 (incógnita 1), testar WebView e um app com OkHttp ou Cronet próprio (incógnitas 3 e 4), e como distribuir o mitmproxy (exigir o cask ou embutir os 88 MB).
