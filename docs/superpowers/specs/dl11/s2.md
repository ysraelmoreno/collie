# S2: o release recusa um helper com a assinatura errada

Contexto: o APK commitado Resources/collie-helper.apk passa a ser assinado com a chave privada do publicador (a assinatura é feita à mão pelo dono, fora do laço). Crie `scripts/verify-device-helper.sh [apk]` (padrão Resources/collie-helper.apk): acha o apksigner (ANDROID_HOME, ~/Library/Android/sdk, versão mais recente de build-tools), roda `apksigner verify --print-certs`, extrai o SHA-256 do certificado e compara com o conteúdo de `Resources/collie-helper.cert.sha256` (uma linha, hex minúsculo, sem dois pontos). Sai com 0 se igual, 1 se diferente (mensagem com os dois valores e o aviso 'assinado com outra chave ou com a chave debug'), 2 se faltar apksigner ou o arquivo de pino (mensagem clara). `--help` sai com 0 sem procurar o SDK. Ligue ao scripts/release.sh (e só a ele) como passo antes de tagar/empacotar: se o verify sair com 1 ou 2, o release para. Crie também `Resources/collie-helper.cert.sha256` com a impressão digital da chave DEBUG atual (placeholder que o dono troca depois de assinar com a chave privada) e documente no README do helper a rotina: build --release, `scripts/verify-device-helper.sh --print` (imprime o SHA-256 do certificado do APK) e gravar o resultado no arquivo de pino. Teste: scripts/test-verify-device-helper.sh com um apksigner falso no PATH (stub que imprime um certificado conhecido): igual passa, diferente falha com 1, sem apksigner dá 2, e o release.sh contém a chamada.
