# h3: `collie work config` mostra o harness e `collie harness explain` testa uma regra

Depende da h1 e da h2. Check: `scripts/check-harness.sh h3` (não o altere). Sem relógio real nem sleep; só `swift test --filter`.

## O que construir
- `work.config` (WorkConfigCommands.swift) inclui o `harness` resolvido (a versão **commitada** do arquivo, como o laço já lê) e os avisos; só leitura, não roda nenhum comando.
- Comando novo `harness.explain` (CLI `collie harness explain "<comando>"`, e MCP): dado um comando, devolve qual regra bateu, o modo e a mensagem, e se `requireBefore` exige um check; não executa nada e **não** pede o token de admin (é só leitura da regra). O texto do comando é dado: o resultado o mostra limpo (sem controle).
- Terminais de agente podem chamar `harness.explain` (para saber o que será recusado), mas nenhum comando de agente altera a harness.
- Atualize `docs/` (referência do `collie-work.json`) com a seção `harness`: exemplo, modos, o que cada camada faz e o que é só config nesta versão (os hooks vêm depois).
## Critérios de aceite (testes em `HarnessCommandTests`, ≥ 8)
- `work.config` lista o `harness` quando existe e omite quando não; usa o commit, não o arquivo sujo do worktree.
- `harness.explain "git push origin main"` devolve a regra, o modo e a mensagem; um comando sem regra devolve `allow`.
- Comando com caractere de controle é limpo na resposta. A rota de agente (token de terminal) funciona; escrever a harness por comando não existe.
- `ProjectWorkConfigTests`, `HarnessConfigTests`, `HarnessMatcherTests` e `CommandsTests` continuam passando.
